# UX-правила и критерии качества интерфейса

Назначение — сделать операции УО интуитивными, массовыми и безопасными. Это **критерии проектирования**, а не перечень готовых дефектов dev56.

## Информационная иерархия
1. **Контекст до команды:** пользователь всегда понимает, какая УО/дом/перечень/год и область действия выбраны.
2. **Текущее состояние:** локально/проект/размещено/изменено/ошибка/историческое/операция выполняется, не технический GUID вместо человеческого статуса.
3. **Одно главное рекомендуемое действие**, меняющееся в зависимости от подтверждённого состояния; объяснять причину блокировки прямо рядом.
4. **Вторичные сетевые и локальные действия** обозначать понятными глаголами и областью (вся УО / текущий дом / месяц / период).
5. **Данные и редактирование:** широкие таблицы сохраняют полезную площадь; контроли для строк — рядом со строками, без ненужного второго верхнего меню.
6. **Опасные действия:** удаление, отмена, аннулирование, повторное заполнение с перезаписью — вторичный контекст и явное предупреждение о последствиях.

## Принципы рабочего процесса
- Сохранять нативные паттерны Windows и Qt: фокус, Enter/Escape/Delete, copy/paste, контекстное меню.
- Не прятать основной массовый сценарий в глубоком меню ради «чистоты» экрана.
- Не делать четыре одинаково заметных primary-кнопки, не заменять ясный процесс декоративными карточками, полосами и абстрактными статусами.
- «Общий выбор» и «независимый выбор» — осознанные режимы пользователя.
- Сначала избегать ошибок UI через доступность и подсказки, затем показывать локальную причину и путь исправления; не скрывать API-ошибку «что-то пошло не так».
- Автосохранение локальных правок не равнозначно сохранению/размещению в ГИС.
- Восстановление после сбоя должно продолжать очередь, а не перезапускать всё с первого месяца.
- При операциях по нескольким домам/месяцам показывать счётчик, прогресс, успешные/пропущенные/ошибочные элементы.

## Responsive desktop и доступность
- Светлая и тёмная темы; проверить selected, disabled, warning, danger, tooltip, меню и диалоги.
- UI-scale 100%, 125%, 150% плюс DPI Windows; шрифты и подписи не должны обрезаться.
- Проверять 1366×768, 1600×900, 1920×1080; допустима вертикальная прокрутка рабочего пространства и горизонтальная в широких таблицах, а не на всём экране.
- Визуальное сообщение не должно зависеть только от цвета; состояния доступны с клавиатуры; фокус после диалогов не пропадает.
- Явные состояния empty/loading/error/success/disabled, с пояснением что делать далее.

## Формат UX-исправления
Для каждого предложения:
- пользователь и цель;
- BEFORE (ссылки на код, скриншот, воспроизведение);
- AFTER (путь, основное/вторичные действия, правила доступности);
- сценарии отсутствия контекста/ошибки/слабой связи/частичного периода;
- локальные/удалённые данные, которые затронет действие;
- минимальные изменения PySide6 и регрессионные тесты;
- отметка CONFIRMED или HYPOTHESIS, ручная проверка Windows при необходимости.

**Проверка «не красивый, а удобный»:** незнакомый с устройством API пользователь должен понимать свою текущую позицию, область действия и следующий шаг без консультации разработчика.

## Методика проверки
Главный протокол — `docs/ux/AUDIT_METHOD.md` (атрибутированные 10 эвристик Якоба Нильсена). Реальные сценарии — `docs/ux/TEST_SCENARIOS.md`, пользовательские свидетельства — `docs/ux/USER_FEEDBACK.md`. Субъективный «красивый вид» не заменяет наблюдаемый результат и безопасную работу.
