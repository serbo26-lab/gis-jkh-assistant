# Неизменяемые ограничения ГИС ЖКХ и пользовательских данных

> Снимок dev56 и проектной истории; перед реализацией проверять текущий код/тесты и актуальные HAR. Документ **не заменяет** нормативные источники и не является спецификацией REST API.

## Достоверность источников
1. Для фактического GIS-запроса — реальный HAR/логи подтверждённой операции и текущий helper. Не придумывать endpoint или body на основе названия кнопки.
2. Для того, что **делает программа** — исходники, migrations/repository, tests и воспроизводимый runtime.
3. Для того, что **нужно изменить** — UX-требование/одобренное решение владельца. Разводить факт, интерпретацию и предложение.
4. Если HAR и текущий код расходятся, фиксировать конфликт и не выполнять разрушительные изменения до проверки.

## База и безопасность
- Пользовательская SQLite и данные приложения находятся отдельно от сборки. Обновление не должно стирать существующую БД, тарифы, перечни, планы, фиксацию, фото, акты.
- Новые поля и структура БД — миграцией. UI-рефакторинг сам по себе не требует изменений бизнес-модели.
- Загрузка из ГИС не даёт права без подтверждения перезаписывать несинхронизированные локальные данные.
- Сохранить remote state объектов, не управляемых приложением. Для принадлежащих приложению объектов хранить remote identity и безопасно выполнять изменение/удаление.
- Browser helper выполняет операции в авторизованной вкладке; логины, cookies, auth headers и личные HAR не переносить в документацию или клиентское приложение.
- Использовать обезличенные примеры (например, `г. М....., ул. Б......, д. 0`).

## Жизненный цикл
- Размещённый перечень имеет зависимые данные — план, фиксацию, оценку. Исторически подтверждена возможность отмены с последующей перестройкой перечня, но отмена в ГИС способна удалить зависимые сведения. Обязательное явное предупреждение.
- Исторический план может содержать больше работ, чем возвращаемый сейчас перечень. Просмотр допустим; нельзя автоматически заменить старые работы новыми и отправить опасный update.
- Тариф — история изменений; цена может меняться внутри года. Не подменять фактическую тарифную историю произвольным тарифом для годового периода; проверять действующую формулу конкретного сценария.
- Периоды управления ограничивают допустимые месяцы перечней; дата окончания управления — первый день без управления в зафиксированной модели.
- Планирование доступно в связке с размещённым перечнем; не скрывать причину отсутствия предпосылки.
- Фиксация: реальные показатели по месяцам, фото и внеплановые работы — раздельные объекты. Повторное сохранение не удаляет существующие remote assets.
- Оценка: создание и сохранение **проекта без актов** допустимо; размещение — после проверки необходимых актов. Удаление remote-акта через проект — отдельный управляемый путь.
- Пользовательские/импортированные акты неприкосновенны для автоформирования; автоакты можно регенерировать только там, где право владения очевидно. Для обычного акта не заполнять поля, относящиеся к ненадлежащему качеству и уменьшению платы.

## Scope и очереди
- «Выбранный месяц» и «Доступный период» — разные области действий. Не считать выбранный месяц единственным основанием готовности всего периода.
- Массовая операция — один осознанный запуск, явный scope, прогресс и остановка на первой существенной ошибке с возможностью продолжить.
- При уже удачно обработанных месяцах/домах не повторять без необходимости и не объявлять неполную очередь успешной.
- Выполняющееся асинхронное действие сохраняет исходные сущности даже если пользователь меняет общую навигацию.
