# GIS Workflow Architect — использование в Codex

## Назначение
Проектный субагент `gis-workflow-architect` живёт в `.codex/agents/gis-workflow-architect.toml`. Он **только анализирует** рабочие процессы (sandbox_mode = read-only): не пишет код, не изменяет БД и не размещает сведения в ГИС ЖКХ.

Настройки соответствуют официальному формату Codex subagents: поля `name`, `description`, `developer_instructions`, `sandbox_mode`. Поле `model` намеренно не закреплено — используется доступная модель основной сессии (например, GPT-6.1 Sol, если она выбрана и доступна); `model_reasoning_effort = "high"`.

## Как вызвать
Открой репозиторий в Codex и попроси явно делегировать задачу:

> Делегируй read-only аудит агенту gis-workflow-architect. Начни с актуального main, проанализируй вкладку «Оценка качества» и переход из «Фиксации». Построй таблицу состояний/действий, найди UX-тупики и спорные переходы с точными ссылками на код. Отдельно проверь сохранение проекта без актов, размещение с актами, общий контекст и scope месяца/периода. Не изменяй код. Разделяй подтверждённые дефекты и предположения. Верни предложения и критерии приёмки.

Для масштабного анализа последовательно пройти 5 вкладок; не запускать несколько агентов, которые одновременно редактируют одни и те же файлы.

## Взаимодействие с остальными агентами VoltAgent
- `gis-workflow-architect` — сценарии, продуктовые состояния, критерии приёмки.
- `ui-designer` — схема расположения, плотность, визуальная иерархия.
- `anti-ui-slop-reviewer` — независимая критика визуального результата.
- `ui-ux-tester` — воспроизводимые сценарии, ошибки взаимодействия.
- `ui-fixer` / `python-pro` — реализация по согласованному ТЗ после разрешения.
- `reviewer` / `accessibility-tester` — независимый контроль регрессий и доступности.
Не нужно устанавливать полный каталог VoltAgent автоматически. Каждый сторонний TOML отдельно проверить до предоставления write-прав.

## Минимальный smoke-check
1. Убедиться, что файл TOML валиден, содержит обязательные поля, находится под `.codex/agents/`.
2. Убедиться, что агент виден текущему Codex (при необходимости начать новую сессию).
3. Попросить агента перечислить реальные пути `workflow_presenter.py`, `workflow_state.py`, `main_window.py` и факт «проект качества без актов можно сохранить».
4. Попросить сравнить месяц vs доступный период, включая частичную готовность.
5. Убедиться, что агент выдаёт конкретные source refs, статус CONFIRMED/HYPOTHESIS и **не меняет файлы**.
6. Для визуального теста дать скриншоты реальных Qt-окон либо среду с запущенным Windows UI. Статический аудит без этого не является визуальной приёмкой.

## Контроль перед изменениями
После анализа отдельный PR для реализации, тесты `pytest`, ревью инвариантов, проверки на Windows и обновление версий **только если менялся продукт**. Не объединять внедрение агента с большим UI-рефакторингом.
