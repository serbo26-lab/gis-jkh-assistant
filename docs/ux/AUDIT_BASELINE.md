## Приоритетные ГИПОТЕЗЫ для следующих проверок
Эти пункты — **направления аудита, а не обнаруженные баги**:
- P1: может ли пользователь сразу понять «текущий шаг / следующий шаг» на каждой вкладке без чтения технических надписей? Нужен визуальный прогон.
- P1: не становятся ли локальные/сетевые команды или месячный scope неоднозначными при переключении из фиксации в качество? Нужен прогон частично заполненного периода.
- P1: как отражаются последствия отмены размещённого перечня и проверяются downstream-зависимости перед подтверждением? Нужен сценарий с обезличенными тестовыми данными.
- P1: насколько ясно отображаются исторические строки: доступность просмотра и причина запрета опасной отправки? Нужен тест со старым перечнем.
- P2: сохраняется ли пространственная иерархия с крупным шрифтом/масштабом на 1366×768 в реальном Windows окружении? Автотесты не заменяют ручного осмотра.
- P2: можно ли однозначно восстановиться после прерванной пакетной операции, не задвоив успешно отправленные месяцы? Нужна проверка очереди с инъекцией ошибки.

## Первые сценарии для проверки агента
1. Качество: проект без актов → сохранение (доступно) → размещение (валидация объясняет, что требуется) → добавление актов → размещение.
2. Фиксация: 2 готовых месяца + 1 пустой → scope «доступный период» → предложить открыть пустой месяц, а не повторно заполнить всё.
3. Общий контекст: выбранный локальный неразмещённый перечень → переход к плану → сообщить причину невозможности вместо молчаливой подмены.
4. Исторический план: старые строки сохранились → просмотр → запрет опасной обратной записи.
5. UI: обе темы, масштаб 100/125/150, 1366×768 и 1920×1080; прокрутка внутри таблицы, а не потеря основных действий.

## Требуемый результат полноценного UX-аудита
По каждому сценарию: воспроизведение, точная ссылка на реализацию, оценка P0/P1/P2, CONFIRMED/HYPOTHESIS, предлагаемое улучшение, тест приёмки и риск для данных. Не объявлять статическое чтение кода итоговой проверкой интерфейса.
